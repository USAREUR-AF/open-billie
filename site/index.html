open-billie

Any sensor in, one track record, three standard formats out.

Open Billie prepares a node, builds a small package for each sensor (a kid), and publishes its data, normalized, as CoT, ASTERIX CAT062 or SAPIENT through Zenoh. The kid decodes; the shared translator writes the format.

What it is

    
A sensor-neutral project for preparing a node, building sensor-specific kid packages, and publishing normalized data through the shared Billie translator and Zenoh path. The node runs Billie locally after installation. Proprietary sensor protocols, decoders, mappings and captures stay outside this repository; the example kid and the sensor simulator use synthetic data.

    

      
The node
One guided install
The wizard checks the release, the node's architecture, SSH access and prerequisites, then installs the platform on Ubuntu Server 24.04, amd64 or arm64. The platform owns local Zenoh, fabric mTLS, routes and the bridge.

      
The kid
A package per sensor
A decoder, a schema, a user-defined mapping and lookups, synthetic conformance vectors and a runtime adapter. A kid needs no fabric credentials and no encoder of its own.

      
The translator
Standard formats out
The shared Rust translator turns the canonical track into CoT XML, an ASTERIX CAT062 Edition 1.21 record, or a SAPIENT BSI Flex 335 v2.0 message, and rejects anything outside the versioned contract.

    

  






  

    
    

      
Where the line is drawn

      
The kid owns the sensor: its wire format, its decoder, and the mapping from its fields to Billie's canonical record. The platform owns everything that touches the network beyond the node. The record crosses between them over a local Unix socket.


Sensor TCP/UDP input
  -> kid decoder and user mapping
  -> canonical record over local Unix socket
  -> shared Rust translator and encoder
  -> local Zenoh route
  -> Open Billie platform mTLS bridge and remote fabric

      
Contracts: decoder to translator, canonical track v2, Zenoh and fabric security.

    

  






  

    

      
Build and deploy a kid

      
The local tools scan and validate kid sources, build a package for linux/amd64 or linux/arm64 with Docker or Podman, and ask which decoder implementation to use when there is more than one. The guided deployment transfers and installs it, lets you choose a declared TCP or UDP listener, and activates it.

      

        
StepCommand

activatesudo billie kid activate oetf

        
      

      
Kid bundles are separate from the platform release and are unsigned; their checksums detect file changes but do not authenticate the builder. Start with the kid package authoring guide and the template.

Take it off again

      
Remove a kid and keep the platform, or remove the platform. Teardown lists what it will remove, asks for confirmation, and asks a second time before deleting node identity and fabric credentials. NetBird is left untouched.


$ sudo billie kid deactivate <id>
$ sudo billie kid remove <id>
$ sudo billie teardown

      
Before updating a node, read the upgrade notes: platform 0.3.0 requires kids built for the v2 canonical track contract. Validation status and open items: testing log.
