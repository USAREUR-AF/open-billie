# Local SBOM review

Review date: 2026-11-03

## Scope and method

Syft 1.55.0 generated SPDX 2.3 JSON from the OCI image inside each checksum-verified OETF 0.2.0 `linux/arm64` candidate bundle. Each SBOM identifies the image by its OCI digest. The generator also verifies the bundle sidecar and the bundle's internal image checksum.

The candidate bundles and SBOMs are in the ignored `dist/sbom-candidate/` directory. They were built from branch `fix/audit-local-release` at commit `d6c77dd` with local source changes present. The bundle metadata does not record the source commit, and the bundles are unsigned. These files are for review and are not release artifacts.

Some package records have a detected `licenseConcluded` expression or a separate package record with a declared license, but those results still need review against the exact package's license and notice files.

## Findings

- The TypeScript runtime workspace package `@open-billie/oetf-runtime-typescript` lacked a license field. Its `package.json` now declares `Apache-2.0`, consistent with the OETF example package. The candidate image was rebuilt and rescanned after that change.
- Compared with the existing OETF TypeScript 0.1.3 image SBOM (560 package records), the current multi-stage TypeScript 0.2.0 image has 317 records. The old image contained build dependencies including TypeScript, Vitest, Vite Node, pnpm, and Changesets packages; none of those package names are present in the current image SBOM. The current image still contains packages supplied by its Node and Debian runtime base images.
- The Python candidate has 25 Debian/Python records with `licenseDeclared=NOASSERTION`. The image includes `/usr/share/doc/<package>/copyright` for 20 names. The remaining records have possible source-package notice evidence in the same image: the `krb5` record has a matching upstream version to `libkrb5-3`; `libgcc-s1` and `libstdc++6` share the installed GCC source version represented by `gcc-12-base`; `systemd` shares its installed source version with `libsystemd0`; and CPython 3.12.10 has `/usr/local/lib/python3.12/LICENSE.txt`. Rust has 18 such Debian records: 15 package-specific copyright files plus the same GCC/systemd source-version evidence for its three remaining package names. TypeScript has 18 Debian records plus `node`: 15 package-specific copyright files plus those same three Debian source-version matches; Node has its separate versioned license bundle described below. A matching source version and a retained notice file are evidence for follow-up, but do not by themselves prove every binary's applicable license or complete the SPDX mapping. Review package-by-package before release.
- Python's six `Simple Launcher` records map to pip's vendored `distlib==0.3.9` Windows launchers. pip's bundled `vendor.txt` confirms the exact distlib version. Distlib 0.3.9 declares PSF-2.0; its tagged `PC/launcher.c` separately carries a two-condition BSD-style notice, applicable to those launchers. The exact notice has been added to `THIRD_PARTY_NOTICES.md`. Syft still reports these generic binary records as `NOASSERTION`; the SBOM has not been manually rewritten.
- The TypeScript `node` record is version 22.14.0. The official Node v22.14.0 source tree has a 140,396-byte `LICENSE` file containing its licensing and bundled third-party notices. The exact file is vendored under `kids/examples/oetf/licenses/` and copied into the runtime image at `/licenses/node-v22.14.0-LICENSE`. The rebuilt image and SBOM confirm that file is present with SHA-256 `1474fea5eff88dc92763acca3ca1f54b51fa153be1529eae74ace35957aea9ce`. The separate npm license does not substitute for Node's license file. This resolves the Node notice omission for this candidate only; regenerate it for release builds. The updated SPDX file hash is `c0ed380889d21cb71545e8a7f8ff33d27481dcaa215014de61cfd875b47d7680`.
- Syft emits 76 distinct `LicenseRef-*` identifiers in the Python SBOM, 66 in Rust, and 67 in TypeScript. Their corresponding SPDX `extractedText` values are `NOASSERTION`; the identifiers largely reflect license labels from Debian copyright metadata rather than full texts. Map these labels to exact license texts and applicable notice obligations before release. The presence of an identifier in the SBOM is not a license approval.
- The SBOMs identify the images and architectures correctly. They do not establish source revision provenance, provide all required license texts, or replace the platform and host dependency inventory.
- Syft also scanned the repository's pinned Zenoh image for `linux/arm64`: `docker.io/eclipse/zenoh@sha256:157965d71e0bfd0a044d76a985ff0e5c306ad3968929168fb9678cd2a7fec23f`. It reported 18 Alpine package records, each with a declared license, and no `LicenseRef-*` expressions. The `zenohd` binary did not appear as a separate package record. The upstream [`zenohd` 1.5.1 manifest](https://docs.rs/crate/zenohd/1.5.1/source/Cargo.toml) declares `EPL-2.0 OR Apache-2.0`, but the image digest has not yet been tied to that exact release, so the daemon's version/license and required notice remain a release gate. The local SBOM is `dist/sbom-candidate/zenoh-linux-arm64.spdx.json` (SHA-256 `79c16ca914f121f7f8302afc14049ede65c6c357c0542285093018ab6d5528c6`).
- A local arm64 platform package `0.3.0+d6c77dd.dirty` was built. Syft's scan of the `.deb` and its extracted payload only identified the top-level Billie package/payload; it did not enumerate the translator's statically linked Rust dependencies or APT `Depends` as resolved package versions. The Rust translator source scan produced one package record and no file records, so it is not evidence of a complete Cargo dependency inventory. `billie-platform-rust-workspace-source.spdx.json` is a zero-byte file and invalid JSON; exclude it from review and release inputs. These scans are not a complete platform SBOM. The node's Ubuntu packages resolve at install time, so capture them on a prepared node and generate a deployment inventory before distribution.

## Release gates still open

1. Regenerate from a clean, committed source revision and include that revision in the bundle/SBOM provenance.
2. Review Debian packages whose `licenseDeclared` is `NOASSERTION`; map packages to exact copyright/license files, including shared source-package documents, and normalize only after evidence is checked. Node's unknown scanner field is covered by a separate version-matched source review and bundled license notice.
3. Review all `LicenseRef-*` expressions against the corresponding files in each image. Confirm the final image retains the complete Debian notices, and collect any third-party license texts not present in the image.
4. Produce a complete platform SBOM that includes translator dependencies and the exact platform package contents. The pinned Zenoh SBOM currently covers arm64; repeat it for each supported architecture and verify the daemon's license/version from vendor metadata. Capture resolved host packages when preparing deployment records.
5. Rebuild, sign, and scan the exact release bundles after the source and notices are finalized. Do not publish these local unsigned candidates as release artifacts.
